# quiz-me（变更理解测验）

针对阶段：实现后、merge 前。长 session 后 agent 完成的东西往往比用户意识到的多；**读 diff 只能得到浅理解，因为大量行为取决于既有代码路径**。测验是强制用户跟上的机制。

原则：**测验全过才 merge**——这是用户保住对自己代码库理解权的把关动作。

## 触发信号

- 用户说「quiz me / 考考我 / 我想确认我理解了这次变更」。
- 长 session 收尾、准备 merge / 提交评审。
- 用户要接手一段不是自己写的 agent 产出。

## 工作流

1. **先给变更报告**（Markdown），让用户带着上下文进考场：
   - 背景与意图：为什么做、解决什么问题；
   - 直觉：方案的核心思路，一段话讲明白；
   - 做了什么：**按行为分组**（不是按文件）列出变化；
   - **与既有代码的交互**：新代码依赖 / 改变了哪些已有路径——diff 看不出、最容易考砸的部分；
   - 边界与风险：edge cases、已知限制、Deviations（有 `implementation-notes` 就直接引用）。
2. **出题**（5~10 题，依变更规模）：
   - 覆盖配比：行为变化 ≥3 题、与既有代码的交互 ≥2 题、边界情况 ≥2 题；
   - 题型：选择题为主（若环境有多选题工具如 ask_user_question 则使用），关键处 1~2 道简答；
   - 好题标准：**答错说明会在生产里踩坑**（「X 情况下会走新路径还是旧路径？」），不考背诵（不问「新增函数叫什么名字」）。
3. **逐题问答**：一次一题；答错 → 讲解正确答案与对应代码位置 → 稍后换一道同考点的新题重考。
4. **判定**：
   - 全对 → 给出「理解达标，可以 merge」的结论；
   - 某考点反复错 → 指出该区域，建议用户亲自读对应代码后重考，**在此之前不建议 merge**。

## 产出

Markdown 变更报告 + 测验记录（题目、作答、讲解、最终判定）。

## 反模式

- 考背诵而非考行为：函数名、文件路径全对也不代表理解。
- 跳过报告直接考：测验的目的是让用户跟上，不是刁难。
- 用户答错就放水通过：「必须全过」是这个技巧的全部约束力。
- 只考新代码、不考它与既有代码的交互：那正是 diff 读不出来的部分。
- 一次性把 10 道题全贴出来：逐题问答才有讲解与重考的空间。

## 示例 prompt（用户视角）

> 「我想确认我理解了这次变更里发生的一切。给我一份变更报告——上下文、直觉、做了什么——最后附一个我必须通过的测验。」
