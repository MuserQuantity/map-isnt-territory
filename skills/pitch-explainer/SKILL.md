# pitch-explainer（提案与讲解文档）

针对阶段：实现后。shipping 的关键一环是他人的理解与批准，而**读者的未知项和你当初的一样多**。这份文档同时做两件事：

- 帮一般读者**加速理解**：他们从你出发时的 unknowns 开始读；
- 帮专家**加速批准**：他们想看到你已考虑过他们会预期的失败点。

## 触发信号

- 「打包成一个文档，我发到群里 / Slack 拿 buy-in。」
- 「给团队写个这次变更的说明。」
- 评审 / 审批前的材料准备。

## 前置输入（缺了就先问）

1. Artifacts：原型、spec、实现笔记（`implementation-notes` 的 Deviations / Surprises 尤其有价值）、demo 录屏或 GIF。
2. **受众**：一般读者还是领域专家？他们最初的未知项是什么？专家会追问哪些失败点？
3. 目的：拿批准 / 征求意见 / 纯同步——决定文档重心。

## 工作流

1. 收集并通读所有 artifacts。
2. **受众未知项分析**：列两张清单——「读者读之前不知道的事」「专家会想确认的失败点」，全文按这两张清单组织。
3. 组稿，推荐结构：
   - **Demo 先行**（GIF / 截图 / 一句话效果）——先让读者看到结果再讲原理；
   - 问题与动机（读者的第一个未知项：为什么要做）；
   - 方案概览（架构 / 流程，配必要图示）；
   - 关键决策与取舍（从 `implementation-plan` 与笔记的 Decisions 提炼）；
   - **已考虑的风险与失败点**（专家最关心；Deviations 与 Surprises 在这里发光）；
   - 现状与后续（未完成项、开放问题）。
4. **单文件交付**：默认 Markdown；需要内嵌 demo / 交互演示时用单文件 HTML。确保能直接粘贴或上传到 IM / 文档平台。
5. 长度纪律：正文 3~5 分钟读完，细节放附录或链接。

## 产出

一份可直接分享的单文件文档（Markdown 或单文件 HTML）。

## 反模式

- 按时间线写成工作日志：读者关心结果与决策，不关心过程顺序。
- 只讲成功不讲考虑过的失败点：专家会认为你没想过，反而拖慢审批。
- demo 埋在第三屏之后：读者没有耐心。
- 多文件交付：分享成本高，必须单文件。
- 无视受众写同一份稿：给专家的和给外行的重心完全不同。

## 示例 prompt（用户视角）

> 「把原型、spec 和实现笔记打包成一个我能直接丢进群里拿 buy-in 的文档。demo GIF 放最前面。」
