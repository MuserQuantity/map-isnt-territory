# interview-me（需求访谈）

针对象限：**Known Unknowns**——用户知道自己还没想清楚的部分，以及 agent 视角发现的歧义。

时机：通常在头脑风暴/原型之后——方向已有共识，但仍残留会影响实现的模糊点。

## 触发信号

- 用户字面说「interview me」「采访我」「问我问题」。
- brainstorm / 原型之后，方案已定但细节仍有多处歧义。
- 用户给的 spec / 需求描述中存在冲突或缺口。

## 前置输入

- 任务上下文（spec、原型、brainstorm 结论、参照物——有什么给什么）。
- 用户提示的重点关注区（可选）。

## 工作流

1. **先做功课再提问**：扫描任务描述与代码库，列出真实存在的歧义清单。不问凭空的通用问题（「你要用什么数据库？」），只问从疆域里挖出来的问题（「现有 User 表用了 soft delete，新功能要沿用吗？」）。
2. **按影响排序**：
   - P0：答案会改变架构（数据模型、模块边界、依赖选型）；
   - P1：答案会改变用户可见行为（UX 流程、边界情况的表现）；
   - P2：实现细节（命名、文案、默认值）。
3. **一次只问一个问题**（严格执行，等回答再问下一个）：
   - 每题附上：为什么这个问题重要 + 你倾向的默认答案及理由；
   - 尽量给 2~4 个候选项降低回答成本（若环境有多选题工具如 ask_user_question 则使用）；
   - 用户答「不知道」时：给默认值并标记为「假设」，或建议转 `brainstorm-prototype`（做出来看）/ `blindspot-pass`（先补认知）。
4. **随答随收敛**：前面的回答可能让后面的问题作废或催生新问题，动态维护清单；P2 问题攒到最后批量确认也可以。
5. **产出决策记录**（模板见下），可直接作为 `implementation-plan` 的输入。

## 决策记录模板

```markdown
# 访谈决策记录：<任务>

| # | 问题 | 决定 | 理由 | 影响范围 |
|---|------|------|------|---------|
| 1 | ... | ... | ... | 架构 / UX / 细节 |

## 假设（用户未确认，按默认执行）
- <假设>：<默认值 + 触发重审的条件>

## 仍开放的问题
- <问题>：<最晚何时必须回答>
```

## 反模式

- 一口气抛 10 个问题：用户会疲劳、浅答。一次一题。
- 先问 P2 不问 P0：细节答得再全，架构错了全作废。
- 不给候选项与默认倾向：开放题回答成本高，容易得到含糊答案。
- 问完不落字：口头共识过了 session 就丢。
- 没做功课就开问：问题应来自代码库和任务的真实歧义，不是问卷模板。

## 示例 prompt（用户视角）

> 「就这个任务里所有模糊的地方，一次一题采访我，优先问答案会改变架构的问题。」
