# reference-mining（参照物挖掘）

针对场景：用户**表达不出**想要的东西——没有语言描述它，或描述成本太高。这时最好的规格不是文字而是参照物；参照物里可以有图表、文档、截图，但**最好的参照是源代码**：它包含行为、结构与构建方式的最丰富细节。

跨语言同样成立：参照物是 Rust，目标是 TypeScript，照样提取语义再重实现。参照网站时读它的底层代码（markup、脚本、样式），而不只是看截图。

## 触发信号

- 「vendor/rate-limiter 这个 crate 的 backoff 行为就是我要的，在我们的 API client 里实现相同语义。」
- 「我喜欢 XX 网站的这个模块，做一个类似的。」
- 「参考 <repo>/<module> 的做法。」
- 用户描述了半天说不清，但能指出一个现成的东西。

## 前置输入（缺了就先问）

1. 参照物在哪：本地路径 / 仓库 / 网站（网站尽量拿到真实 markup 与脚本）。
2. **参照哪一面**：行为语义？视觉外观？API 设计？性能策略？——不问这个最容易做偏。
3. 目标位置与技术栈约束。

## 工作流

1. **读源码**：优先读实现而非 README；测试用例往往是最精确的行为规格。
2. **提取语义并分三层**：
   - **本质语义**：用户点名要的行为（如 backoff 曲线、重试上限、抖动策略）；
   - **结构选择**：可照搬、也可按目标栈惯例替换的部分；
   - **偶然细节**：参照物特有、不应带过来的东西（它的日志框架、错误码风格、历史包袱）。
3. **产出语义摘要**（模板见下）让用户勾选：哪些保留、哪些按目标栈重做、哪些丢弃。**跳过这步直接动手，最容易把参照物的偶然细节一起搬过来。**
4. **重实现**：语义忠实 + 表达遵循目标代码库惯例（命名、错误处理、测试风格）。
5. **对照检查**：逐条核对语义摘要；行为关键处写测试对齐（同输入同输出/同曲线）。

## 语义摘要模板

```markdown
# 参照物语义摘要：<参照物> → <目标>

## 本质语义（默认保留）
- [ ] <行为>：<参照物中的位置 + 一句话描述>

## 结构选择（建议按目标栈重做）
- [ ] <选择>：<参照做法 → 建议的目标做法>

## 偶然细节（默认丢弃）
- <细节>：<为什么不带过来>
```

## 反模式

- 逐行翻译而非语义重实现：把参照语言的习惯硬塞进目标栈。
- 只看文档/截图不读源码：拿到的是宣传而非行为。
- 不区分本质与偶然：连参照物的坑一起复刻。
- 语义摘要没经用户确认就开工。

## 示例 prompt（用户视角）

> 「vendor/rate-limiter 这个 Rust crate 实现了我想要的 backoff 行为。读一遍，在我们的 TypeScript API client 里重实现相同语义。」

> 「我很喜欢这个网站的定价页模块。读它的底层代码（不是截图），告诉我它是怎么搭的，然后在我们的营销页里做一个同样质感的。」
