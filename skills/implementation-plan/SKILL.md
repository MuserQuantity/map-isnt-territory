# implementation-plan（决策导向的实现计划）

针对阶段：实现前的最后一步——把前序发现（brainstorm 结论、访谈决策、参照语义摘要）收敛成可 review、可执行的计划。

核心原则：**计划是给用户挑刺用的，不是给 agent 备忘用的**。所以按「被用户改动的概率」排布内容，而不是按执行顺序或文件顺序——让 agent 主动暴露用户最可能想改的东西。

## 触发信号

- 用户说「写个 plan / 实现计划 / 方案文档」。
- interview / brainstorm 已完成，动手前需要收敛。
- 长任务开工前，用户想 review 一遍关键决策。

## 前置输入

- spec / 原型 / 访谈决策记录 / 参照语义摘要（有什么收什么）。
- 用户特别关注或明确放权的部分（可选）。

## 工作流

1. 通读输入与相关代码，列出全部待做决策。
2. **按变动风险分层**：
   - **高风险**（放最前、逐个展开）：数据模型变更、新类型/接口、用户可见流程、对外契约；
   - **中风险**：模块边界、依赖选型、错误处理策略；
   - **低风险**（放最后、一句话带过）：机械重构、改名、搬文件——标注「这部分请信任我」。
3. 每个高风险决策写四件事：**方案、被否掉的备选、选择理由、日后改变它的代价**。
4. 标注**即兴空间**：实现中允许 agent 自行应对的情况类型 + 应对原则（如「遇到未预见的 edge case：选保守方案、记入 Deviations、继续」——与 `implementation-notes` 衔接）。
5. 附 review checklist，引导用户只看高风险区。

## 计划模板

```markdown
# 实现计划：<任务>

## 请重点 review（按你最可能想改的排序）

### 1. 数据模型
<变更内容 | 被否掉的备选 | 选择理由 | 日后更改的代价>

### 2. 类型 / 接口
...

### 3. 用户可见行为
...

## 中风险决策
- <决策>：<方案 + 理由>

## 机械性改动（简述，请信任）
- ...

## 即兴空间（执行期协议）
- 遇到 <情况类型> 时：<应对原则>

## Review checklist
- [ ] 数据模型可接受？
- [ ] 接口命名 / 形状可接受？
- [ ] 用户可见变化可接受？
```

## 产出

Markdown 计划文档（模板见上）。批准后的计划连同 spec / 原型一起，作为新实现 session 的输入（配合 `implementation-notes` 执行）。

## 反模式

- 按执行顺序平铺 20 步：用户找不到该看哪，review 变成走过场。
- 机械部分写得比数据模型还详细：噪声淹没信号。
- 只给一个方案不留决策痕迹：用户无从判断你是否考虑过别的路。
- 计划定死到没有即兴空间：执行期遇到意外只能硬套或停摆——好计划允许 agent 在框架内即兴。

## 示例 prompt（用户视角）

> 「写一份实现计划，把我最可能想调整的放在最前面：数据模型变更、新类型接口、所有用户可见的东西。机械性重构放到最底下，那部分我信任你。」
