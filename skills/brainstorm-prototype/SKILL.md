# brainstorm-prototype（头脑风暴与一次性原型）

针对象限：**Unknown Knowns**——用户说不出口、但见到就能认出的隐性标准（典型如视觉设计、交互手感、文案口吻）。也用于编码 session 开场划定 scope。

为什么要早做：隐性标准在原型期发现很便宜，在实现期发现很贵——spec 的小变化可能导致实现的巨大差异，而且 agent 回滚既有改动比从头做更困难。头脑风暴还能防止 scope 定得太窄（漏掉高价值方向）或太宽（见树不见林）。

## 触发信号

- 用户对「要什么」只有模糊感觉，需要看到具体的东西才能反应。
- 视觉/设计/体验类决策（「我没有视觉品味，也不知道有什么可能」）。
- 编码 session 开场，还没定 scope（几乎每个 session 都值得以探索开场）。
- 用户想在接后端/加状态之前先看一眼 UI 效果。

## 前置输入（缺了就先问）

1. 要探索的维度（布局？配色？信息架构？技术方案？干预点？）。
2. 用户的起点与倾向（有没有已排除的方向）。
3. react 的方式（看图？点一点？读文字方案？）。

## 工作流

### A. 方案头脑风暴（文字类）

1. 先探索代码库/问题空间，不要凭空发散。
2. 产出 5~10 个方案，**沿某个轴排序**（如从最便宜到最有野心），每个 2~3 句：核心思路、代价、适用条件。
3. 用户标注「哪些有共鸣」，追问并记录反应背后的标准。
4. 收敛出 scope，写成一句明确的范围声明。

### B. 一次性原型（视觉/交互类）

1. 做 **3~4 个差异显著的方向**——是截然不同的方向，不是同一方向的微调。
2. 原型纪律：
   - 单文件（默认 HTML）+ 假数据；
   - 不接后端、不管真实状态、不追求代码质量；
   - 明确标注「一次性，不会进入代码库」，放临时目录。
3. 用户 react。
4. **关键一步：把用户 react 时说出口的标准记录下来**（「原来我在意留白」「不要卡片阴影」），沉淀进需求/spec——这是把 Unknown Knowns 转成 Known Knowns 的时刻。
5. 需要时基于中意方向再迭代一轮（这轮可以做同方向微调）。

## 产出

- 头脑风暴：Markdown 方案清单 + 用户反应记录 + 收敛后的 scope 声明。
- 原型：一次性 HTML 文件（临时目录）+ Markdown「设计标准记录」。
- 两者都可直接作为 `implementation-plan` 的输入。

## 反模式

- 几个方向长得差不多：失去让隐性标准显形的能力。
- 原型写成生产代码：接真实 API、加状态管理——原型应该便宜到可以随手扔。
- 用户挑完就结束，不记录**为什么**挑这个：下次还是说不清标准。
- 用户连「好」的判断力都没有时硬做原型挑选：先退回 `blindspot-pass` 补认知（参见 finding-unknowns 中发布视频调色的案例）。

## 示例 prompt（用户视角）

> 「我想给这份数据做个 dashboard，但我没有视觉品味也不知道有什么可能。做一个 HTML 页面，放 4 个截然不同的设计方向，我来挑。」

> 「先别接任何东西，做一个单 HTML 文件、用假数据 mock 新的编辑器工具栏。我想先对布局有个反应，你再碰真实应用。」

> 「我的问题很粗糙：用户在 onboarding 后流失。搜一遍代码库，brainstorm 10 个可以干预的位置，从最便宜到最有野心排序，我会告诉你哪些有共鸣。」
